# Defect Register

Split out of `docs/Fitted_Spec_v2.md` §23 at S4a (`docs/plans/maintainability.md` D6a). This file is
the defect work queue plus its fixed archaeology; §23 keeps the design holes. No silent defects: a
newly found defect is registered here in the same edit that finds it (the same rule §23 states for
design holes).

**Classifier (a count is meaningless without one — maintainability.md §2):** a row lives here when its
subject is incorrect, missing, or harmful behavior of shipped code, tests, or ops measured against
their own intended contract — something whose closure is a **fix**. A row whose subject is an
undecided design question, a capability gap, or a spec/ambition conflict stays in §23 — its closure
is a **ruling or a build**. Pre-M5-era rows whose resolution text became spec contract (e.g. H14,
H55) stay in §23 with the design holes.

**Status vocabulary (D6c, closed set, enforced by hygiene check 8):** `**OPEN**` |
`**FIXED: <sha>**`. One row, one status; a row with a fixed half and an open half is split into two
rows. Severity and arming conditions live in the row body, never in the status — this vocabulary
deliberately has no `BLOCKED`: a defect is open until fixed, and "arms when X lands" is body prose.

**IDs and citations:** rows keep the single `H<n>` sequence shared with §23 — a new row takes the
next unused ID across BOTH files, and IDs never repeat across them. Rows here are cited as
`DEFECTS-H<n>`; §23 rows as `§23-H<n>`; `[[H<n>]]` links may point across the two files and resolve
by grep.

Row bodies are preserved in full from §23 — the byte win of the split comes from the move, not from
compression (compression of closed rows is S4b's, deliberately not done here). Where a row's old
free-text status carried more than the closed vocabulary (severity, landing notes), that text was
relocated verbatim into the resolution column as a leading italic parenthetical.

| H87 | **A rejected Mongo connect promise is cached for the life of the lambda instance, so ONE transient Atlas failure permanently bricks that instance.** `lib/mongodb.ts:31-44` assigns `cached.promise = mongoose.connect(...)` and never clears it on rejection (`cached.conn` is only set on success). After a single failed connect — Atlas M0 is shared, throttled and SRV-addressed, so an SRV blip or a maintenance stepdown inside the driver's default 30s server-selection window suffices — every later `connectMongo()` on that warm instance re-awaits the SAME rejected promise and throws instantly, with no retry, **even after Atlas is healthy again**, until Vercel recycles the instance (which low traffic makes slow). `connectMongo` sits under `lib/apiAuth.ts` and `lib/session.ts`, so the instance loses authentication too — this is not one broken feature but the whole app for whoever routes to it. Found independently by two audit lanes and by direct read. (2026-07-26 deployed-app audit.) | **OPEN** | *(highest-severity live defect.)* The canonical Next/Mongoose cached-connection form, one line: wrap the await so a rejection clears the cache — `try { cached.conn = await cached.promise } catch (e) { cached.promise = null; throw e }` — letting the next request retry. Land with H88; until both are in, the failure presents to a friend as a login problem. |
| H88 | **A database failure is reported to the user as an expired login.** Both auth helpers wrap `initDatabase()` inside the SAME `try` as token verification and map every throw to 401: `lib/apiAuth.ts:31-40` → `"Invalid or expired token"`, `lib/session.ts:30-38` → `"Invalid or expired session"`. Any Mongo fault (H87's bricked instance, an M0 connection-cap rejection, a slow cold connect) therefore surfaces as an auth failure rather than a 503. The friend is told to sign in again, does so successfully at Firebase, and still fails — because the real fault is the database, and nothing in the UI can say so. The client gates compound it: `RedirectIfAuthenticated.tsx:48` and `AuthGate.tsx:25-41` fire `/api/auth/sync` for its side effect and never check `res.ok`, so a 500 there still admits the user into a fully-rendered app in which every later call returns 404 "User not found". (2026-07-26 deployed-app audit.) | **OPEN** | *(diagnosis-corrupting.)* Split the two failure classes: verify the token first, then connect, and map a connect/query throw to 503 with a "trouble reaching your closet" message, reserving 401 for genuine token rejection. Check `res.ok` on the sync call instead of admitting a user who has no Mongo row. |

(2026-07-26 read-only bug hunt, round 2.) | **OPEN** | *(wasted spend, honest failure.)* Branch on the captured `finish_status`: on an abnormal/length finish, either skip the retry outright (the fallback is reached one call sooner and cheaper) or retry with a **reduced** `candidate_requested` and a truthful instruction ("return fewer outfits"), which is the only variant that can actually succeed.
